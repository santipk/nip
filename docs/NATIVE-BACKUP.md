# Respaldo portable cifrado

El respaldo usa un archivo age con contraseña del usuario, cuyo contenido es un tar con manifest versión 2 (restauración compatible con versión 1), catálogo, historial portable por registros e índice/blobs de adjuntos. El catálogo incluye identidad privada e invitaciones; sólo se escribe dentro del flujo cifrado. La biblioteca age implementa cifrado y derivación de contraseña; NIP no implementa criptografía propia. Referencia: [age 0.12.1](https://docs.rs/age/0.12.1/age/struct.Encryptor.html).

El historial se obtiene de snapshots mediante la API de backup de SQLite, incluyendo WAL. Los snapshots temporales conservan payloads DPAPI; los registros se descifran en memoria y se pasan al flujo age. No se copia un archivo SQLite vivo ignorando WAL.

La restauración sólo acepta un destino nuevo. Valida versión, inventario, IDs, canales y mensajes, consume el flujo autenticado completo y vuelve a proteger los datos con DPAPI de la cuenta que importa. No habilita red, reconexión, autoarranque de servidores ni inicio con Windows. La activación posterior es explícita; no mantener online dos copias de la misma identidad.

La API pública es `backup::export(&Store, destino, SecretString)` y `backup::restore(archivo, perfil_nuevo, SecretString)`; ambas son asíncronas y devuelven inventario de servidores, mensajes, archivos y bytes. La integración de exportación debe mantener el gate de mutación de los anfitriones mientras se crean los snapshots; el catálogo se captura antes del primer await. El trabajo de cifrado, archivo y disco corre fuera del runtime de red. La restauración no inicia servidores ni modifica la clave de inicio con Windows.

El exportador no reemplaza un archivo existente y el importador no fusiona ni reemplaza perfiles. Los fallos eliminan el staging de la operación. Cada registro de mensaje tiene límite de 64 KiB, el catálogo de 16 MiB y el manifest de 2 MiB; no se carga todo el historial en RAM. Nombres de entradas del archivo nunca se usan para extraer rutas arbitrarias. Se verifica el stream age completo, incluido el tag final después del terminador tar, antes de publicar el perfil.

Se probaron restauración con WAL vivo y rechazo de contraseña incorrecta, manipulación, truncamiento y destinos existentes en perfiles QA bajo una misma cuenta Windows. El flujo está integrado en Perfil; falta comprobar otra cuenta/equipo; las pruebas locales demuestran que los payloads portables ya no dependen de DPAPI de origen, pero no certifican esa prueba externa. No se ha inyectado un disco físicamente lleno. El gate se repitió con blobs y un outbox confirmado pendiente de publicar. Antes de liberar los gates de mutación, se fijan los blobs inmutables con enlaces físicos temporales (o copia cuando no están disponibles); el cifrado posterior no bloquea voz. Se validan referencias bidireccionales entre historial, índice y publicación, tamaño y SHA-256 de cada blob.
